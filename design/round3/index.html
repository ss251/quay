How it works

From a folder to production in three steps

Each step is one command, and the contract on your account records it. Nothing is overwritten: a release you sealed last week still opens at its URL.

  1. ~/sitesealed
    $ quay deploy ./site -m "second board"
8 files, 1.1 KB new, 5.2 KB reused
1/1 index.html
2  …i7qkbbp3.testnet.page/r/2/

    1Deploy

    quay deploy uploads the folder in chunks, skips bytes the account already stores, and prints a preview URL.

  2. 5harbour office, new lookSealed

    The release gets a permanent id. Its files, message and byte count are fixed, and /r/<id>/ keeps serving that build.

    3Promote or roll back

    The host root follows the production pointer. quay rollback swaps it with the previous release. No re-upload.

CI

A CI key that can preview, and cannot ship

Give your pipeline a publish-only key. Every pull request gets its own sealed preview. Moving production still takes the owner.

  • Scoped on chain. The key may call put_chunk and seal, nothing else.
  • Refused twice. The CLI exits 3 before sending a promote, and the contract rejects one sent anyway.
  • Shown once. quay keys create --ci prints the secret for QUAY_CI_KEY and keeps a 0600 copy outside the repo.

Cost

You pay for bytes, not builds

NEAR locks storage on the account that holds it. Quay prints the estimate before it spends, and stores a file once even if ten releases use it. Delete a release that is not production and its bytes unlock on the same account.
